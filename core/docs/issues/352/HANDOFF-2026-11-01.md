## 1. What this work is

Two things that were separate met:

- **LayerFS's Windows-native Store route** (#352, owner 2026-10-25): SQLite,
  the named-mutex writer lane, the local-NTFS kernel guard and owner-only DACLs
  run natively on Windows; the SDK's Store face (fs, branch, project,
  operator) runs in the caller's process. No WSL2, no daemon.
- **The dsh LayerFS plugin** (`Ephemeral-AI-Lab/dsh-layerfs`), which had only
  the macOS/Windows **worker** design: a long-lived Linux container per home.

The instruction that shaped the end state: **everything must run natively on
Windows** — no WSL2, no Linux worker. So the plugin had to be able to run on
the Windows-native route, and the route had to stop being a set of local patches.

## 3. How the native route is selected now

```yaml
# <DSH_HOME>/profiles/web/cordis.patch.yml
- id: layerfs-host
  config:
    route: native        # Windows only; worker is the other value
```

- `route: native` → the plugin sets `spec.native`, `worker: false`, keeps no
  deployment gaps, hands the runtime `native: true`, and gives project clients
  the Windows home plus the volume's NTFS Store path.
- The runtime picks `platform/native-windows`: no worker endpoint is ever
  handed to `@layerfs/agent`, `status()` reports `docker: not-used` and no
  worker, `start/restart/docker` refuse `Unsupported`, `init` is a no-op, a
  project's volume is a directory under the home, `homeNames` reads the Windows
  home.
- `LAYERFS_NATIVE=1` / `DSH_LAYERFS_NATIVE=1` still work as aliases for scripts
  that predate the setting. The environment is no longer the contract.

## 4. What the route serves, and what it does not

| Call | Native route | Why |
| --- | --- | --- |
| `project.*` (except sandboxes), `fs.*`, `branch.*` | **works** | Direct Store access, in this process |
| `fs.write`, `fs.apply`, `fs.edit`, `fs.rm`, `fs.mv`, `branch.fork/merge/publish` | **works** | Each is one Commit; `main` moves only through `branch.publish` (a direct write is `ReadOnly`) |
| `sandbox.*`, `workspace.*`, `project.list_sandboxes` | **`Unsupported`** | Owner boundary: Workspace/FUSE/Exec/daemon stay Linux-only |
| Views over a project (`/layerfs/project/<name>/{state,history,list,read,runtime}`) | **works** | Sandbox lists come back empty rather than failing (`46fc17b89`, `0eb007e`) |

The consequence that survives all of the above, and the reason section 6 exists:
**an agent in a dsh session on this route can read and commit, but cannot run a
command** — no `npm install`, no build, no test, no dev server, no preview.
Every write is its own Commit, which is fine (a multi-file change is one
`fs.apply`), but nothing verifies that the result runs.

## 6. The open problem: running commands natively on Windows

The owner requires native Windows, so the WSL2 worker (route 1) is out. FUSE on
Windows would be WinFsp (a third-party kernel driver). Research on 2026-11-01:

| Option | Semantics | Component | Admin | Cost on large trees |
| --- | --- | --- | --- | --- |
| **ProjFS** (Projected File System) | OS-level projection: a real directory, content on demand, writes/creates/deletes delivered as notifications — the same capture path FUSE feeds on Linux | **built into Windows** (`Client-ProjFS`) | one elevated enable | placeholders only, near-zero disk |
| Materialize + watch | a real directory filled from the Store; `ReadDirectoryChangesW` narrows the write-back to touched paths | none | no | the whole tree on disk per mount |
| WinFsp | FUSE-compatible kernel driver | third-party driver | install + driver | as ProjFS, but a new kernel component in the trust boundary; our Rust `fuser` would not reuse its C-API compatibility layer |
| Windows containers | isolation only | container runtime | yes | cannot run Linux images |

**Findings that make ProjFS the target:**

- `windows-sys 0.61.2` — already a dependency — carries
  `Win32::Storage::ProjectedFileSystem`; the bindings need no new crate.
- `layerfs-workspace` is ports/adapter (`OverlayRead`, `OverlayJobs`); FUSE lives
  only in `operations/kernel_*` and the separate `layerfs-fuse` crate. The
  design already anticipates other adapters ("each future adapter needs its own
  live mounted proof"), and the range ioctl ABI deliberately names no
  FUSE/WinFsp type.
- **Not enabled on the current machine**: `C:\Windows\System32\projectedfslib.dll`
  is absent and the session is not elevated.

**The one action required** (elevated PowerShell; Windows 11 usually needs no reboot):

```powershell
DISM /Online /Enable-Feature /FeatureName:Client-ProjFS /All
```

**Proposed order, invariant to which backend wins:** define the workspace
backend port (`mount / exec / capture / unmount`), keep the commit path where it
is (the overlay), then add adapters:

1. **ProjFS adapter** — the target: real directory, on-demand content, live
   capture. Needs the feature enabled, then a live mounted proof (an ordinary
   process `cd`s in, runs a command, writes and deletes, and the changes come
   back as one Commit).
2. **Materialize + watch adapter** — the fallback that needs no system change;
   ships `workspace.exec` today, at the cost of writing the tree to disk.

Both funnel into the same overlay and Commit path, so building one does not
waste the other.
